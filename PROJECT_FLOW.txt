2. SECURITY / REQUEST GATEWAY
-------------------------------------------------------------------------------
[DONE] `/api` prefix for every backend route (src/routes/api/index.ts)
[DONE] X-API-Key header guard on every /api/* route (src/plugins/api-key-guard.ts)
       - Timing-safe comparison against API_KEY env var
[DONE] Auth gateway order on protected /api/* routes:
       1) X-API-Key (portal/client gate)
       2) JWT access token verification (`app.authenticate`)
       3) Per-user permission grant (`checkPermission`) — Admin bypasses
[DONE] JWT access tokens (src/plugins/jwt.ts, src/utils/token.ts)
       - SHORT-LIVED: default 15 minutes (`JWT_ACCESS_TOKEN_TTL_SECONDS=900`)
       - Expired access tokens return 401 with code TOKEN_EXPIRED so a
         client can call the refresh endpoint instead of forcing login
       - `app.authenticate` populates request.user = { userId, role }
[DONE] Refresh tokens (src/models/refresh-token.model.ts)
       - Opaque random token; only SHA-256 hash stored in `refresh_tokens`
       - Columns: id, userId, tokenHash, expiresAt, revokedAt, timestamps
       - Default lifetime 7 days (`REFRESH_TOKEN_TTL_DAYS`)
       - Rotated on every successful refresh (old row revoked)
[DONE] Role-based access control - coarse tier (src/middleware/rbac.ts)
       - `requireRole(...roles)` preHandler restricts a route to specific roles
[DONE] Role-based access control - fine-grained tier (inside each *.service.ts)
       - e.g. "HR can only manage Employee records", "cannot delete own account"
[DONE] Per-user, per-endpoint permission system (src/middleware/permission-guard.ts)
       - `permissions` table: id, userId, path (route pattern e.g. /api/users/:id),
         method (GET/POST/PUT/PATCH/DELETE), status (ACTIVE/INACTIVE)
       - `checkPermission` middleware runs after app.authenticate: looks up an
         ACTIVE grant for (current user, route pattern, HTTP method); 403 if none
       - ADMIN role always bypasses this check (prevents total lockout)
       - Wired into users / roles / attendance / permissions routes

    routes -> controller -> service -> validation (zod) -> repository -> DB

5. USER REGISTRATION & AUTH  (src/modules/auth/)
-------------------------------------------------------------------------------
[DONE] POST /api/auth/register  - PUBLIC self-registration (API key only)
       - Always creates the account with the EMPLOYEE role (default)
       - Returns accessToken (15m) + refreshToken (+ user)
[DONE] POST /api/auth/login     - PUBLIC login (API key only)
       - Verifies email + bcrypt-hashed password
       - Returns accessToken (15m) + refreshToken (+ user); refresh hash
         persisted in `refresh_tokens`
[DONE] POST /api/auth/refresh   - PUBLIC refresh (API key only, no JWT)
       - Body: { refreshToken }
       - Looks up hash in DB; if valid + not expired + not revoked:
         rotates refresh token and returns a new accessToken + refreshToken
       - If invalid/expired/revoked: 401 INVALID_REFRESH_TOKEN → login again
[DONE] Passwords hashed with bcrypt (src/utils/password.ts, model hooks on
       User: beforeCreate / beforeUpdate)

6. USER MANAGEMENT [EMPLOYEES / HR / ADMIN]  (src/modules/users/)
-------------------------------------------------------------------------------
[DONE] User model (src/models/user.model.ts)
       - UUID primary key, unique email, firstName, lastName, password (hashed),
         mobile, address, roleId (FK -> roles), timestamps, soft delete (paranoid)
       - toJSON() override strips password from every response
[DONE] POST   /api/users        - create user (Admin creates HR/Employee, HR creates Employee only)
[DONE] GET    /api/users        - list users, paginated (Admin sees all, HR sees Employees only)
[DONE] GET    /api/users/:id    - get one user (scoped: Admin any, HR Employees only, else self)
[DONE] PUT    /api/users/:id    - update own profile fields (name/mobile/address/password)
[DONE] PATCH  /api/users/:id/role - Admin-only dedicated role allocation endpoint
       - Allocating extra ADMIN accounts through the API is always blocked
[DONE] Single-admin guarantee (belt-and-suspenders, 2 layers):
       - Validation: `allocateRoleSchema` only accepts HR/EMPLOYEE — ADMIN is
         not even a valid enum value for PATCH /api/users/:id/role
       - Service: `assertCanAssignRole` (user.service.ts) runs a real COUNT
         query (`userRepository.countByRoleName`) whenever role=ADMIN is
         requested via POST /api/users; if an admin already exists ->
         409 CONFLICT "Only one admin account is allowed"; otherwise 403
         (admin accounts are only ever provisioned by the DB seeder)
       - Seeder: `20260805130200-seed-initial-data.cjs` checks for an
         existing ADMIN user before inserting one, so re-running after a
         `db:seed:undo` (even with a different ADMIN_EMAIL) can't create
         a second admin
[DONE] DELETE /api/users/:id    - soft delete (cannot delete self or an Admin account)
[DONE] Zod validation on all create/update bodies (email format, password
       strength, mobile format, etc.)
[DONE] GET /api/users/stats     - admin dashboard headcount: { totalActive,
       totalInactive, byRole: { ADMIN/HR/EMPLOYEE: { active, inactive } } }
       - "active" = not soft-deleted, "inactive" = soft-deleted (kept for
         history, not a separate boolean column)
       - Admin: sees every role; HR: scoped to EMPLOYEE only (same
         visibility rule as GET /api/users); Employee: 403
       - Registered before GET /api/users/:id so "stats" isn't swallowed
         as an :id param

9. ATTENDANCE MANAGEMENT  (src/modules/attendance/)
-------------------------------------------------------------------------------
[DONE] Attendance model (src/models/attendance.model.ts)
       - One row per user per calendar date (unique userId+date)
       - status: PRESENT | ABSENT | HOLIDAY
       - checkInTime / checkOutTime / workingHours (auto-computed on checkout)
       - Attendance is tracked Monday-Friday only
[DONE] POST /api/attendance   - mark today's attendance (upsert, TODAY only)
       - status=PRESENT: first call records check-in, a later same-day call
         fills in check-out; working hours auto-calculated
       - status=ABSENT: employee can self-declare absent for today directly,
         no approval needed
       - Rejected outright for any date other than today, and on weekends
[DONE] GET  /api/attendance          - list attendance (Employee: own only,
       HR: Employees only, Admin: everyone) with pagination + filters
       (date, status, userId)
[DONE] GET  /api/attendance/:id      - get a single attendance record (scoped)
[DONE] No DELETE endpoint for attendance at all - history is never deletable
       through the API (audit trail integrity)

   -- Downloadable monthly report -----------------------------------------
[DONE] GET /api/attendance/report?month=&year=&userId=&format=csv|json
       - Employee: always own report only; requested month/year must fall
         within a rolling 6-month window (current month + previous 5) -
         older or future months are rejected
       - HR/Admin: may target ANY user via ?userId= (defaults to self if
         omitted); NO 6-month cap - the only floor is that user's own
         account-creation month (can't report on a month before they
         existed); HR is still limited to Employee targets, same as the
         rest of the module
       - Report = daily records (date, day, status, check-in/out, working
         hours) for the month + a summary (total weekdays, present/absent/
         holiday counts, unmarked days, total working hours)
       - format=csv (default): actual file download - Content-Disposition
         attachment, opens directly in Excel/Sheets
       - format=json: same data as structured JSON (for a future frontend)
       - Subject to the same checkPermission grant system as every other
         attendance route (Admin bypasses; HR/Employee need an ACTIVE grant
         for GET /api/attendance/report)

   -- Correction requests / "claims" for PAST dates -----------------------
[DONE] AttendanceCorrectionRequest model (src/models/attendance-correction-request.model.ts)
       - Separate table: userId, attendanceId (nullable), requestedDate,
         requestedDay, requestedStatus (PRESENT/ABSENT/HOLIDAY),
         requestedCheckInTime/CheckOutTime/WorkingHours, reason,
         status (PENDING/APPROVED/REJECTED), reviewedBy, reviewedAt, reviewNote
[DONE] POST /api/attendance/corrections           - raise a claim
       - requestedStatus=PRESENT: time-correction claim, past dates only
       - requestedStatus=ABSENT / HOLIDAY: can also target today
       - Nothing in the main `attendances` table changes yet - PENDING only
[DONE] GET  /api/attendance/corrections            - list claims (scoped by role)
[DONE] GET  /api/attendance/corrections/:id         - get one claim (scoped)
[DONE] PATCH /api/attendance/corrections/:id/review - approve/reject (Admin/HR only)
       - APPROVE is the ONLY code path that ever writes a past date into the
         `attendances` table - patches the existing row or creates a new
         backfilled one, using the claim's requestedStatus/times
       - REJECT leaves `attendances` untouched
       - HR may only review claims raised by Employees

10. CRON JOBS  (src/jobs/)
-------------------------------------------------------------------------------
[DONE] node-cron scheduler wired into server bootstrap/shutdown (src/jobs/index.ts)
       - startCronJobs() called after DB connects & server starts listening
       - stopCronJobs() called during graceful shutdown
       - ENABLE_CRON_JOBS env flag can disable both jobs entirely
[DONE] Job 1 - Attendance reminder (src/jobs/attendance-reminder.job.ts)
       - Runs 08:00, Monday-Friday (CRON_TIMEZONE env, default UTC)
       - Emails every active user who has NOT yet marked today's attendance,
         reminding them to log in and mark it
[DONE] Job 2 - Auto-absence marker (src/jobs/attendance-absence-marker.job.ts)
       - Runs 19:00, Monday-Friday
       - Any active user with NO attendance row at all for today is
         automatically marked ABSENT in the `attendances` table, then emailed
       - Users who already marked PRESENT / ABSENT / HOLIDAY are left alone
[DONE] Both jobs skip themselves entirely on weekends (belt-and-suspenders,
       on top of the Mon-Fri cron schedule)
[DONE] Email utility (src/utils/mailer.ts) - nodemailer wrapper
       - Best-effort send: NEVER throws; if SMTP_HOST/USER/PASSWORD aren't
         configured, logs a warning and skips sending instead of failing the
         job (attendance still gets marked in the DB either way)

2. SECURITY / REQUEST GATEWAY
-------------------------------------------------------------------------------
[DONE] `/api` prefix for every backend route (src/routes/api/index.ts)
[DONE] X-API-Key header guard on every /api/* route (src/plugins/api-key-guard.ts)
       - Timing-safe comparison against API_KEY env var
[DONE] Auth gateway order on protected /api/* routes:
       1) X-API-Key (portal/client gate)
       2) JWT access token verification (`app.authenticate`)
       3) Permission grant on the user's CURRENT role (`checkPermission`) — Admin bypasses
[DONE] JWT access tokens (src/plugins/jwt.ts, src/utils/token.ts)
       - SHORT-LIVED: default 15 minutes (`JWT_ACCESS_TOKEN_TTL_SECONDS=900`)
       - Expired access tokens return 401 with code TOKEN_EXPIRED so a
         client can call the refresh endpoint instead of forcing login
       - `app.authenticate` populates request.user = { userId, role }
[DONE] Refresh tokens (src/models/refresh-token.model.ts)
       - Opaque random token; only SHA-256 hash stored in `refresh_tokens`
       - Columns: id, userId, tokenHash, expiresAt, revokedAt, timestamps
       - Default lifetime 7 days (`REFRESH_TOKEN_TTL_DAYS`)
       - Rotated on every successful refresh (old row revoked)
[DONE] Role-based access control - coarse tier (src/middleware/rbac.ts)
       - `requireRole(...roles)` preHandler restricts a route to specific roles
[DONE] Role-based access control - fine-grained tier (inside each *.service.ts)
       - e.g. "HR can only manage Employee records", "cannot delete own account"
[DONE] Per-role, per-endpoint permission system (src/middleware/permission-guard.ts)
       - `permissions` table: id, roleId (required, no userId at all), path
         (route pattern e.g. /api/users/:id), method (GET/POST/PUT/PATCH/DELETE),
         status (ACTIVE/INACTIVE)
       - `checkPermission` middleware runs after app.authenticate: resolves the
         requester's CURRENT role from their JWT, then looks up an ACTIVE grant
         for (that roleId, route pattern, HTTP method); 403 if none. Matching by
         current role (not a per-user snapshot) is what lets a role change take
         effect immediately, with nothing to re-grant.
       - ADMIN role always bypasses this check (prevents total lockout)
       - Wired into users / roles / attendance / permissions routes

8. PERMISSION MANAGEMENT  (src/modules/permissions/)
-------------------------------------------------------------------------------
[DONE] Permission model (src/models/permission.model.ts) - PURELY role-scoped
       access grant: { id, roleId, createdBy, path, method, status }. There
       is no userId for WHO the grant applies to at all - a grant is "role
       X may METHOD PATH", full stop. `checkPermission` resolves the
       requester's CURRENT role from their JWT and looks up an ACTIVE grant
       for that role (see `hasAccess` / `findActiveGrant`). This is what
       makes a role change (e.g. Employee promoted to HR, an "exceptional
       case") take effect immediately - there's no per-user row tied to the
       old role to clean up, and nothing to re-grant for the newly-promoted
       user.
       - `createdBy` is a separate, REQUIRED audit field: WHO granted it
         (the acting admin's user id, taken server-side from the
         authenticated requester - never from the request body). Its FK
         is ON DELETE RESTRICT, so a user who has created grants can't be
         hard-deleted while those grants still exist.
[DONE] POST   /api/permissions       - create a grant for a role: { role,
       path, method, status } (Admin only); one row covers every user
       currently holding that role, and anyone moved into it later;
       createdBy is auto-stamped from the authenticated admin's own id
[DONE] GET    /api/permissions       - list grants, optionally filtered by roleId (Admin only)
[DONE] GET    /api/permissions/:id   - get one grant (Admin only)
[DONE] PUT    /api/permissions/:id   - edit a grant's path/method/status (Admin only)
[DONE] DELETE /api/permissions/:id   - revoke a grant (Admin only)
[DONE] `checkPermission` middleware enforces these grants on every guarded
       request (see section 2) - matches the actual Fastify route PATTERN,
       not the resolved URL, so one grant covers every resource at that endpoint

9. ATTENDANCE MANAGEMENT  (src/modules/attendance/)
-------------------------------------------------------------------------------
[DONE] Attendance model (src/models/attendance.model.ts)
       - One row per user per calendar date (unique userId+date)
       - status: PRESENT | ABSENT | HOLIDAY
       - checkInTime / checkOutTime / workingHours (auto-computed on checkout)
       - Attendance is tracked Monday-Friday only
[DONE] POST /api/attendance   - mark today's attendance (upsert, TODAY only)
       - status=PRESENT: first call records check-in, a later same-day call
         fills in check-out; working hours auto-calculated
       - status=ABSENT: employee can self-declare absent for today directly,
         no approval needed
       - Rejected outright for any date other than today, and on weekends
[DONE] GET  /api/attendance          - list attendance (Employee: own only,
       HR: Employees only, Admin: everyone) with pagination + filters
       (date, status, userId)
[DONE] GET  /api/attendance/:id      - get a single attendance record (scoped)
[DONE] No DELETE endpoint for attendance at all - history is never deletable
       through the API (audit trail integrity)

   -- Downloadable monthly report -----------------------------------------
[DONE] GET /api/attendance/report?month=&year=&userId=&format=csv|json
       - Employee: always own report only; requested month/year must fall
         within a rolling 6-month window (current month + previous 5) -
         older or future months are rejected
       - HR/Admin: may target ANY user via ?userId= (defaults to self if
         omitted); NO 6-month cap - the only floor is that user's own
         account-creation month (can't report on a month before they
         existed); HR is still limited to Employee targets, same as the
         rest of the module
       - Report = daily records (date, day, status, check-in/out, working
         hours) for the month + a summary (total weekdays, present/absent/
         holiday counts, unmarked days, total working hours)
       - format=csv (default): actual file download - Content-Disposition
         attachment, opens directly in Excel/Sheets
       - format=json: same data as structured JSON (for a future frontend)
       - Subject to the same checkPermission grant system as every other
         attendance route (Admin bypasses; HR/Employee need an ACTIVE grant
         for GET /api/attendance/report)

   -- Correction requests / "claims" for PAST dates -----------------------
[DONE] AttendanceCorrectionRequest model (src/models/attendance-correction-request.model.ts)
       - Separate table: userId, attendanceId (nullable), requestedDate,
         requestedDay, requestedStatus (PRESENT/ABSENT/HOLIDAY),
         requestedCheckInTime/CheckOutTime/WorkingHours, reason,
         status (PENDING/APPROVED/REJECTED), reviewedBy, reviewedAt, reviewNote
[DONE] POST /api/attendance/corrections           - raise a claim
       - requestedStatus=PRESENT: time-correction claim, past dates only
       - requestedStatus=ABSENT / HOLIDAY: can also target today
       - Nothing in the main `attendances` table changes yet - PENDING only
[DONE] GET  /api/attendance/corrections            - list claims (scoped by role)
[DONE] GET  /api/attendance/corrections/:id         - get one claim (scoped)
[DONE] PATCH /api/attendance/corrections/:id/review - approve/reject (Admin/HR only)
       - APPROVE is the ONLY code path that ever writes a past date into the
         `attendances` table - patches the existing row or creates a new
         backfilled one, using the claim's requestedStatus/times
       - REJECT leaves `attendances` untouched
       - HR may only review claims raised by Employees

13. REDIS RESPONSE CACHE  (src/database/redis.ts, src/utils/cache.ts)
-------------------------------------------------------------------------------
[DONE] ioredis client (src/database/redis.ts), connected to REDIS_HOST/PORT/
       PASSWORD/DB from .env (defaults: localhost:6379, db 0)
[DONE] Treated as a "best effort" dependency, NOT a hard one like Postgres:
       - Boot only does a non-blocking PING for a startup log line, never
         fails/delays server startup if Redis is down
       - Every cache read/write is wrapped in try/catch (src/utils/cache.ts);
         a Redis failure is logged and treated as a plain cache miss - GET
         endpoints keep serving correct data straight from Postgres either way
       - `retryStrategy` keeps trying to reconnect in the background forever
[DONE] Cache-aside helper `withCache(logger, key, loadFresh, ttl?)`:
       returns the cached value if present, otherwise calls `loadFresh`
       (the repository call), caches the result (JSON, default TTL from
       CACHE_TTL_SECONDS, 300s), and returns it
[DONE] `invalidateNamespace(logger, namespace)`: SCAN + DEL every key under
       a namespace prefix (e.g. `cache:users:*`) - called after every
       create/update/delete so the very NEXT GET call recomputes fresh data
       instead of serving stale cache (TTL is just the safety net)
[DONE] Cached (list + get-by-id, plus admin stats where relevant):
       - Users: GET /api/users, GET /api/users/:id, GET /api/users/stats
         (cache key includes requester role since HR/Admin see different data)
       - Roles: GET /api/roles, GET /api/roles/:id
       - Permissions: GET /api/permissions, GET /api/permissions/:id
       - Attendance: GET /api/attendance, GET /api/attendance/:id
       - Corrections: GET /api/attendance/corrections, .../corrections/:id
       Invalidated on: create/update/delete/allocate-role for users; create/
       update/delete for roles; create/update/delete for permissions;
       mark-attendance + correction-approval + the 7pm auto-absence cron
       job for attendance; raise/review for corrections
[NOT CACHED, intentionally]
       - `hasAccess` (the per-request permission check in
         permission-guard.ts) — this runs on literally every guarded
         request, and correctness there matters more than the speedup;
         kept always-real-time against the database
       - GET /api/attendance/report — high-cardinality (month/year/user)
         and rarely requested twice in a row; not worth the cache-key complexity
[DONE] Mutation helpers that share a lookup with a public GET (e.g.
       `findRoleOrThrow`, `findUserOrThrow`, `findPermissionOrThrow`,
       `findAttendanceOrThrow`, `findCorrectionOrThrow`) are NEVER cached —
       only the public read functions (`getRoleById`, `getUserById`, ...)
       wrap them in `withCache`, so update/delete always mutate a live
       Sequelize row, never a cached plain object
